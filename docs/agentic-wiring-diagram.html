Fluxnova BPM — architecture note

The Agentic Wiring Diagram

Every connection in this system — modeler to engine, engine to worker, worker to model, worker to tool — is one of exactly three things: an HTTP request/response, a locally spawned process talking over stdin/stdout, or a server-sent event stream. Nothing exotic, nothing engine-specific. That's the whole reason it's feasible to bolt agentic behavior onto Fluxnova without touching the engine: every new capability is a new HTTP call or a new spawned process, on the worker side, in userland.

Companion piece: Who Calls Whom traces one tool-call, request by request, across four architectures. This note zooms out to the whole system and the other legs that doc didn't cover — the Modeler, the human, and the parts that don't exist yet but slot into the same shape.

Notice what's not on this diagram: no arrow starts at the Engine and points outward at anything external. Every outbound call to the model, a tool, or a market-data API originates from a worker — a plain process the engine knows nothing about beyond "something is polling my REST API." That single design choice is what makes the rest of this document possible: the engine's job stays exactly what it's always been (track state, hand out work, wait for answers), and "agentic" is a property of what's polling it, not a property of the engine itself. Two edges run between agent-task-worker and MCP servers on purpose — the same worker reaches a local one over stdio and a remote one over HTTP, covered in leg 04.

Modeler → Engine: shipping a diagram

02

Engine → Worker: the one contract everything else stands on

proven — agent-task-worker + portfolio-task-worker

Both workers built this session — one that calls an LLM, one that's pure arithmetic — speak the identical protocol to the engine. This is the single generic primitive: the External Task API. Learn this once, and every worker (agentic or not) is just a different thing happening between fetchAndLock and complete.

This is a long-poll-flavored pattern, not a push — the worker asks, the engine answers immediately with whatever's ready (possibly nothing). The engine is 100% passive here: it never initiates contact with a worker, never knows a worker's address, and would function identically if you swapped every worker in this diagram for a different language, a different machine, or a completely different team's code. That's what "zero engine changes" actually cashes out to in practice.
03

Worker → Model: the reasoning leg

proven — FX + Time, Morning Portfolio Review

Once agent-task-worker has a locked task, it's a plain HTTPS client to whichever model provider you configured — gpt-4.1-mini in every demo this session. This call happens 1–8 times per task execution (the tool-calling loop), each round-trip either ending the loop with a final answer or asking for more tool calls.

The tool schemas sent on every call aren't hand-maintained — they come from whichever tools were discovered as siblings in the ad-hoc sub-process (leg 04/06). Add a new MCP server as a tool child and, with zero code change here, the next task execution's very first call to the model already offers it.
04

Worker → Tool: three transports, one interface

proven — real Polygon.io + Finnhub, live data

Who Calls Whom traces each of these request-by-request; this table is the summary a worker's tool-dispatch code actually branches on. All three live behind the identical invokeTool(tool, args) call — the LLM never knows or cares which one it triggered.

TransportWhat happensProven with
Plain HTTP tool One fetch() to a URL you configured by hand, method/headers/body templated with the LLM's arguments. Agent Tool (HTTP) — FX rate demo
MCP — stdio (local) spawn() a child process, JSON-RPC over its stdin/stdout: initialize → tools/list (schema discovered, not hand-written) → one or more tools/call, then the process is killed. mcp-server-time, Polygon.io (uvx), Finnhub (npx)
MCP — HTTP (remote) Same three JSON-RPC methods, but each one is a POST to a URL instead of a pipe — the server can live on a completely different machine. Built and tested (fx-rate-mcp-http-server.js); not used in the live Portfolio demo
The two real bugs this session hit here are worth keeping in mind for the next one: Polygon's published release pinned an incompatible SDK version (fixed with a uv dependency override), and the worker wasn't actually loading its own .env file, so newly-added API keys silently never reached spawned subprocesses until --env-file was added explicitly. Neither bug was in the architecture — both were the kind of thing that only surfaces by actually running real external services, not by reasoning about the design.

Engine → Human: making a poll-based system feel instant

proven — Morning Portfolio Review chat loop

Nothing about BPMN or the External Task API is naturally fast — everything so far in this document is request/response or poll/wait. Getting a human-in-the-loop chat to feel like a live conversation rather than a form you submit into a queue takes three separate tricks stacked on top of the same primitives, not a different protocol.

Call this "tachyon-like" with one honest asterisk: the feedback is close to instant — every log line streams the moment it's written, the UI never leaves you staring at a spinner with no information — but the answer still takes as long as a tool-calling LLM loop actually takes, typically 5–25 seconds in this session's real runs. What's fast is the illusion of continuous progress; what's honestly bounded by physics (network round-trips to a model provider, subprocess spin-up for MCP servers) is the actual reasoning. This session also hit a concrete engine-side limit worth knowing about here: a chat that runs long enough can grow its memory past a database column's length limit and fail — fixed by capping and trimming what gets persisted, but a good reminder that "fast and unbounded" isn't free even with SSE doing the UI work.
06

Recipe: building an agent directly in Fluxnova

proven — every Agent Task in this session

No engine code, no new deployment artifact beyond the BPMN itself. The whole trick is one existing BPMN primitive, used in a way its designers probably didn't picture but never prohibited either.

  1. Wrap the agent in an ad-hoc sub-process. Ad-hoc sub-processes support an activeTasksCollection — an expression naming exactly which child activities the engine is allowed to schedule. Everything else inside the container exists in the diagram but is never entered.
  2. Add one orchestrator task — a bpmn:serviceTask, camunda:type="external", topic agent-task — and list only its id in activeTasksCollection. This is the one task the engine actually runs.
  3. Add tool children as siblings — more bpmn:serviceTasks, same container, not listed in activeTasksCollection. The engine parses them, validates them, draws them — and never schedules them. They're pure configuration, read by the worker, not the engine.
  4. Point the worker at the topic. agent-task-worker locks the orchestrator task, reads the deployed process XML itself (one HTTP GET), finds every sibling tool inside the same ad-hoc container, and turns each into a callable function schema for the model.
  5. Run the loop inside one task execution. Model call → tool dispatch → model call, as many times as Max Iterations allows, entirely inside the worker's handling of that single locked task. The engine only ever sees one fetchAndLock and one complete — the whole reasoning loop is invisible to it.
This is why it's "feasible to add agentic capabilities to Fluxnova" as a general claim, not just a description of what already exists: nothing above is Fluxnova-specific engine behavior beyond the pre-existing activeTasksCollection mechanism. Any process, in any diagram, gets an agent by following this same five-step recipe — it composes with whatever else is already in the process.
07

Recipe: invoking an external MCP or Agent

proven — Polygon.io, Finnhub, mcp-server-time

The load-bearing insight here: MCP has no concept of "tool" versus "agent." A tools/call can be answered by three lines of arithmetic or by an entire autonomous multi-step agent running behind that one endpoint — the protocol, and everything agent-task-worker does with it, is identical either way. Connecting Fluxnova to someone else's agent is the same recipe as connecting it to a weather API.

  1. Add an Agent Tool (MCP) child to the same ad-hoc container as the orchestrator — same rules as leg 06, excluded from activeTasksCollection.
  2. Choose a transport. Transport: Local (stdio) with a Command/Command Arguments the worker will spawn (uvx, npx, a plain script) — or Transport: Remote (HTTP) with a Server URL if the agent/tool already runs as a service.
  3. The worker connects once per task execution — spawns or POSTs initialize, then tools/list. Whatever that external agent chooses to expose becomes real, callable functions; nothing is hand-typed on the Fluxnova side.
  4. Every discovered tool is namespaced serverName__toolName so one Agent Task can safely mix several external agents/tool providers at once — this session's Portfolio demo ran Polygon and Finnhub side by side this way, 41 tools offered to one model call.
  5. The model decides what to call, if anything — a question that only needs one provider's data never touches the other. Nothing forces every connected agent to be consulted every time.
A tool provider that doesn't speak MCP at all still fits — that's leg 04's plain HTTP path, and it's the same shape one level down: point at a URL, template the arguments in, read the response back as text. MCP buys schema discovery and multi-tool-per-connection; hand-written HTTP buys "works with literally any endpoint that returns text," including an external agent's own webhook-style API if that's all it offers.

Extending outward: webhooks in and out

proposed — not built this session

Nothing in this session wired up a webhook, in either direction — worth being direct about that rather than implying it's proven. But the shape is a direct extension of legs already built, not a new mechanism.
